[not live-verified against a real arm64 host pulling/running the image — only that the workflow YAML parses and the Dockerfile has no arch-specific assumption]. Skipping `/app/data`: fresh admin password + empty DB every restart, **and** invalidates every admin session (Data Protection keys live there too — see below). `/app/certs` holds `ca.pfx` (internal CA, 10-year validity) and `server.pfx` (agent-facing TLS leaf, regenerated whenever `UPDATEWATCH2_SERVER_HOSTNAME` changes) — losing it invalidates every already-approved agent's certificate on the next restart, same as losing `/app/data` invalidates sessions. `/app/agent-updates` (`updatewatch2-server#14`) holds the currently-known-newest agent release's downloaded assets — losing it is less permanent: `AgentUpdateService.CheckForUpdatesAsync` verifies every recorded asset filename still exists on disk on every periodic tick, not only when GitHub reports an actually-new version, and re-downloads (outcome `Redownloaded`, audit-logged as `agent-update.assets-redownloaded`) the moment one is missing — a real, initially-shipped gap (the original only re-downloaded on a version change, so losing this volume without a GitHub bump in between left a stale `AgentUpdateState` row 404ing agents indefinitely, until the disk check was added for the unchanged-version path too).

## Commands (server)

Requires the .NET 10 SDK (`dotnet --version`). All commands run from `server/`:

```
dotnet build                                    # build the whole solution
dotnet test                                     # run all tests (unit + integration)
dotnet test --filter FullyQualifiedName~Auth    # run one test class/namespace
dotnet run --project src/UpdateWatch2.Server    # run the API (SQLite db created/migrated at server/data/updatewatch2.sqlite)
dotnet ef migrations add <Name> --project src/UpdateWatch2.Server --startup-project src/UpdateWatch2.Server --output-dir Db/Migrations   # after changing an entity or AppDbContext — bump Db/SchemaVersion.cs alongside it
```

`dotnet-ef` is a separate global tool (`dotnet tool install --global dotnet-ef`) if not already on `PATH`.

The SQLite connection string is resolved lazily via DI (`Program.cs`), reading `Database:Path` from configuration at `AppDbContext` construction time — not eagerly at startup. Keep it that way: resolving it eagerly breaks configuration overrides applied by `WebApplicationFactory` in tests (bit us once — see the Auth/Api test isolation fix in the initial scaffold commit).

The admin session is a cookie (`UpdateWatch2.Auth`, `SameSite=Lax`), not a bearer token — `web/`'s API client always sends `credentials: 'include'`. CORS is configured (`Cors:AllowedOrigins` in `appsettings.json`, default `http://localhost:5173`) with `AllowCredentials()`, which requires an explicit origin list — `AllowAnyOrigin()` and credentialed requests are mutually exclusive per the browser spec, so don't "simplify" this to a wildcard. In `WebApplicationFactory`-based tests, seed the admin account directly via `AppDbContext` (see `TestHelpers/AuthTestHelper.cs`) rather than relying on the app's own startup seeding — that seeding already ran with an unknown random password by the time a test looks, so the helper must overwrite the existing row's hash, not skip when one exists (raced and produced confusing 401s once — see the auth-wiring commit).

**Bug: `builder.Logging.SetMinimumLevel(...)` does not work in `Program.cs`.** ASP.NET Core's host logging re-reads `Logging:LogLevel:*` from `IConfiguration` reactively, and `appsettings.json`'s `Logging:LogLevel:Default` ("Information") wins over the imperative call regardless of order — `LogDebug`/`LogTrace` were silently discarded even with `SetMinimumLevel(LogLevel.Debug)` in effect [confirmed by hand: temporary marker calls plus a live server, zero output either way, on both `UPDATEWATCH2_LOGLEVEL` and a DB-persisted level]. Fix: write the value ASP.NET Core's own config-driven filter actually reads — `builder.Configuration["Logging:LogLevel:Default"] = <"Debug"|"Information"|"Warning"|"Error">` — done this way in `Program.cs` today. If you touch that block, re-verify live (grep console output for `^dbug:` lines) — this bug produced zero compiler warnings and zero failing tests.

**Bug (server v0.30.2): changing the log level via the admin UI had zero effect on a running container's `docker logs`** — reported by the user as "the Docker container's logging is still broken." Root cause: a known, deliberately-scoped-out limitation (`IAdminSettingsStore.LogLevel`'s doc comment used to say so outright); a fresh install defaults to `INFO`, but once an admin changed it, `docker logs` showed almost nothing afterward (even basic host-startup lines), since a level like `WARNING` suppresses those too. Fix: `AdminSettingsStore.Apply` now pushes a changed level onto the running `IConfiguration`'s `Logging:LogLevel:Default` key on every settings load/update (`LogLevelMapper`, shared with `Program.cs`'s own pre-`Build()` write) — **but that alone wasn't sufficient** [confirmed by a throwaway harness before shipping, and a full xUnit test, `AdminSettingsStoreTests`]: mutating a value through `IConfigurationRoot`'s indexer does **not** itself raise that root's own reload/change token (only an underlying provider's own reload mechanism, or an explicit `IConfigurationRoot.Reload()` call, does), and `IOptionsMonitor<LoggerFilterOptions>` only re-checks when that token fires — without an explicit `Reload()` right after the indexer write, `ILogger.IsEnabled(...)` never changed post-startup. This is why `Program.cs`'s own pre-`Build()` write never needed its own `Reload()`: nothing has read/cached `LoggerFilterOptions` yet at that point, a fundamentally different situation from mutating an already-cached value on a fully running host. [live-verified end to end against a real Docker container: `PUT /api/admin/settings` with `logLevel: "DEBUG"`, then — with no restart — the very next request produced fresh `dbug:`-level EF Core log lines in `docker logs`].

**A user-driven line-by-line review of a full log-level audit (`log-level-audit.md`) found real gaps in the audit itself before it found anything to change** — worth remembering next time one is produced. Asked to extend it after noticing it missed `"Start processing HTTP request..."`/etc., the grep-based methodology (every `logger.LogX(...)` call in this repo) turned out to structurally miss messages emitted by referenced libraries themselves: `Microsoft.Extensions.Http`'s automatic per-request logging on the one `AddHttpClient<IGitHubReleaseClient, GitHubReleaseClient>` typed client (four messages, later a fifth), EF Core's connection/command/transaction/migration/change-tracking logging (by far the loudest Debug source in the whole server), and Generic Host's own hosting-lifetime messages — plus the discovery that `appsettings.json`'s `"Microsoft.AspNetCore": "Warning"` override permanently caps a swath of ASP.NET Core's own internal logging (routing, MVC, auth, CORS, static files) below whatever `LogLevel` says. The user asked to demote the `IGitHubReleaseClient` HttpClientFactory messages (five, in the end) from Information to Debug (server v1.3.26), since they're redundant to this repo's own shorter result/error lines for the same calls — not a simple severity edit, since a library's own hardcoded message severity can't be changed at the call site. Fix: a new `LogLevelMapper.ToHttpClientLoggingCategoryValue` gates the category dynamically ("Debug" only when the effective LogLevel is genuinely DEBUG, "Warning" — a complete mute — otherwise), written by both `Program.cs`'s pre-`Build()` resolution and `AdminSettingsStore.Apply`'s live re-application for `System.Net.Http.HttpClient.IGitHubReleaseClient.{LogicalHandler,ClientHandler}`, inheriting the same no-restart guarantee. **A fifth message found only while implementing this**: "HTTP request failed after {ElapsedMilliseconds}ms" (EventId 104, also Information, full exception/stack trace on a genuine transport failure) — the user chose to demote this one too, rather than promote to Warning, since this repo's own explicit Warning/Error logging (`AgentUpdateService`'s "Failed to check GitHub for a new agent release", the same call these `AgentUpdateCheckWorker`/`AgentUpdateService` GitHub checks trigger) already reports the identical failure more concisely. [live-verified against a throwaway harness with a real `AddHttpClient` client pointed at a deliberately unreachable host: at "INFO" none of the five lines appear even on a genuine connection-refused error with a full stack trace; at "DEBUG" all five appear exactly as before]. The agent side got the equivalent treatment the same day (agent v1.0.22) for its own `AddHttpClient<IServerClient, ServerClient>` — see Commands (agent).

Data Protection keys (encrypt/sign the auth cookie) are persisted to `<Database:Path's directory>/keys` — co-located with the SQLite database's directory rather than the container's ephemeral default (`~/.aspnet/DataProtection-Keys`), so they ride along on the same `/app/data` volume with no separate config knob. Losing that directory (or running without the volume mounted) logs out every admin session on the next restart even though nothing else changed [live-verified: login, `docker restart`, same cookie still worked] — don't move the keys off that volume without re-verifying the same way.

**Bug: the auth cookie's `SecurePolicy` used to be `CookieSecurePolicy.Always`, not `SameAsRequest` — broke exactly the plain-HTTP `docker run` walkthrough in this README.** `Always` marks the cookie `Secure` unconditionally; a real browser then silently refuses to store it over plain HTTP (the container's `ASPNETCORE_ENVIRONMENT` is `Production` by default, no dev-only escape hatch). Login still returned 200 with the right body — the browser just quietly never had a session, and the next API call 401'd, silently read by `AuthProvider`'s handler as "log out and bounce to `/login`", no error shown anywhere. Fix: `CookieSecurePolicy.SameAsRequest` plus `app.UseForwardedHeaders()` (with `KnownProxies`/`KnownIPNetworks` cleared, trusting `X-Forwarded-Proto` from the expected reverse proxy) — plain HTTP gets a non-Secure cookie that actually gets stored, and a TLS-terminating proxy in front still gets a Secure one. `AuthControllerTests` has explicit `Login_over_plain_http_...`/`Login_over_https_...` tests constructing `WebApplicationFactoryClientOptions.BaseAddress` by hand: **`WebApplicationFactory.CreateClient()`'s default base address is `http://localhost`, not `https://`** [confirmed by hand] — so nothing else in the suite ever exercised the `Secure`-flag branch, and .NET's own test `HttpClient`/cookie jar doesn't reliably reproduce a real browser's Secure-cookie enforcement anyway — assert on the literal `Set-Cookie` header string, not on whether the same client keeps sending the cookie, or a regression here can pass tests while still broken for real users.

To build/run the Docker image locally: `cd docker && docker compose up --build` (or `docker build -f docker/Dockerfile -t updatewatch2-server .` from `server/`, then `docker run -p 8795:8795 -v uw2-data:/app/data updatewatch2-server`). `docker/docker-compose.yml`'s comments cover the mount points and env vars.

`ActiveDirectoryAuthService`'s LDAP bind/search/group-membership logic was first verified only by hand, against a real OpenLDAP server: `docker run osixia/openldap:1.5.0`, seed a user + `groupOfNames` group via `ldapadd`/an LDIF, `PUT /api/admin/settings` with `adUserSearchFilter` set to `(&(objectClass=inetOrgPerson)(uid={0}))` (OpenLDAP's schema), then hit `/api/auth/login` for: a group member with the right password (succeeds), wrong password (fails), right password but *not* a group member (fails — the important one), unknown username (fails). **That manual scenario is now an automated regression test too** (`updatewatch2-server#13`): `tests/UpdateWatch2.Server.Tests/Auth/ActiveDirectoryLdapIntegrationTests.cs` reproduces the identical four cases against the identical image, seeded from `tests/UpdateWatch2.Server.Tests/Auth/ldap-seed/bootstrap.ldif`. Deliberately not the Testcontainers NuGet package (its own issue's "suggested approach") — it transitively pulls in SSH.NET, which carries a known high-severity CVE (GHSA-q939-rpr3-3284) for an SSH-exec feature never used here — `scripts/run-ldap-test-server.sh` drives the same container via plain `docker` CLI calls instead, shared between local dev (`up`/`down`) and a dedicated `ldap-integration-test` CI job (`continue-on-error: true`), kept out of the main `test` job's `dotnet test` via a `[Trait("Category", "LdapIntegration")]` filter — the same "don't let the newer/less-certain piece block the core pipeline" precedent the agent repo's `linux-packages` job already established. **Running this for real (not just writing it) caught two real bugs**: the seed LDIF must be `docker cp`'d into the container rather than bind-mounted — the image's own entrypoint `chown`s and later `rm`s that directory, which fails outright against a real host bind mount, and silently deleted the LDIF off the host the first time before the fix; and `AdOptions.Encryption` defaults to `StartTls`, which fails against this plaintext-only test container with the same generic "could not connect" message a genuinely unreachable host produces — three of the four tests had been silently passing for the wrong reason (every authenticate call was failing to connect at all, which happens to also satisfy an assertion expecting failure) until the one test expecting success exposed it. If you touch `ActiveDirectoryAuthService`, run `dotnet test --filter Category=LdapIntegration` (after `scripts/run-ldap-test-server.sh up`) rather than trusting a plain `dotnet test` alone.

**`ActiveDirectoryAuthService` rejects an empty password before attempting the user-DN bind — do not remove this guard.** RFC 4513 §5.1.2 defines an LDAP simple bind with a non-empty DN but a zero-length password as an *unauthenticated* bind, which a compliant server (including real AD) accepts without checking the password at all. Without the explicit `string.IsNullOrEmpty(password)` check up front, submitting any valid/guessed directory username with an empty password would silently pass that bind and authenticate as that user — a full auth bypass, not theoretical. [Caught by an automated security review after the AD login feature's initial commit, not hand-testing — the manual OpenLDAP verification above never happened to try an empty password]. `Auth/ActiveDirectoryAuthServiceTests.cs` covers it with a fake `IAdminSettingsStore` pointed at an unreachable RFC 5737 test-net host: the assertion is that the call fails *fast* (milliseconds, via a short `CancellationTokenSource`), proving the guard runs before any network bind — if missing, the test would hang until TCP connect timeout instead of cleanly failing, so don't weaken this test to just "eventually returns false".

**Two Kestrel listeners, configured explicitly in `Program.cs`'s `ConfigureKestrel` — never rely on `ASPNETCORE_URLS` again.** Port 8795 (default; `Kestrel:HttpPort` overrides) stays plain HTTP for the browser-facing admin UI, reverse-proxy-terminated. Port 8796 (`Kestrel:AgentPort`) is Kestrel-direct-TLS-terminated, no proxy, dedicated to agent mTLS. Both defaults were deliberately chosen as uncommon port numbers (not 8080/8443) to reduce collision odds — `ClientCertificateMode.AllowCertificate`, not `Require`, because agent registration must be reachable with no client certificate at all (an agent has none at first contact); every other agent route is gated by the separate `AgentCertificate` authorization policy instead. An explicit `ListenAnyIP` call replaces `ASPNETCORE_URLS` entirely [confirmed by hand] — the Dockerfile's old `ENV ASPNETCORE_URLS=...` line was removed; setting it again would be silently ignored. **8080/8443 were later renumbered to 8795/8796 project-wide** (server v0.19.0, agent v0.14.0) — Kestrel port defaults, the Dockerfile's `EXPOSE`/healthcheck, `docker-compose.yml`, both `.env.example` files, and `AgentOptions.ServerPort`'s default (plus installer prompts and starter config) all moved together, since 8080/8443 are common enough to collide with something already running. An already-deployed instance relying on the old defaults (rather than an explicit `Kestrel__HttpPort`/`Kestrel__AgentPort` override) needs its external port mapping updated on the next redeploy.

**Bug: Kestrel's `HttpsConnectionAdapterOptions.ClientCertificateMode` alone is not enough for an internal CA — you also need an explicit `ClientCertificateValidation` callback that accepts unconditionally, or every agent request silently fails at the TLS handshake, before any application code runs.** [Confirmed by hand, not from docs]: `HttpsConnectionMiddleware` runs its *own* default client-certificate validation (chain-building against the OS trust store) at the raw TLS layer, entirely separate from and *before* the `Microsoft.AspNetCore.Authentication.Certificate` middleware's `CustomTrustStore` logic ever runs. An agent leaf signed by the internal CA is never in the OS store, so Kestrel aborted the handshake itself on every agent request — surfaced as a bare connection reset, not any HTTP status code, logged only at Debug. Fix, in `Program.cs`'s `UseHttps` call: `https.ClientCertificateValidation = (_, _, _) => true;`, deferring all trust decisions to the authentication middleware where `CustomTrustStore` actually lives. [Only found by a live end-to-end run — `WebApplicationFactory`'s in-memory `TestServer` bypasses Kestrel/real TLS entirely and can't exercise this at all].

**Bug: `CertificateRequest.Create(X509Certificate2 issuerCertificate, ...)`'s convenience overload requires the issuer and leaf to use the *same* key algorithm — it throws rather than cross-sign.** This project's internal CA is RSA 4096 (root) signing ECDsa P-256 (leaves) by design, so this bit immediately; fix is the `X509SignatureGenerator` overload instead (`X509SignatureGenerator.CreateForRSA(rootCertificate.GetRSAPrivateKey(), RSASignaturePadding.Pkcs1)`), which does support cross-algorithm signing. Also always compare thumbprints via `certificate.GetCertHashString(HashAlgorithmName.SHA256)`, never the legacy `X509Certificate2.Thumbprint` property (SHA-1) — both `InternalCertificateAuthority`/`CertificateValidator` and (agent-side) `WindowsClientCertificateStore` deliberately avoid `X509Store`'s built-in `X509FindType.FindByThumbprint`, which compares against that same legacy SHA-1 value and would silently never match.

**Bug: `AgentsListPage`/`AgentDetailPage` didn't auto-refresh** — server-side state changes needed a manual browser reload. Fixed by polling both pages every 5s (`POLL_INTERVAL_MS`) via `setInterval`, cleared on unmount; a background poll failure deliberately does NOT flip the page into its hard error/not-found state (a `hasLoadedOnceRef` guard — only the very first load failing does that), so a transient network hiccup doesn't blank an already-rendered list/agent. Real test coverage with `vi.useFakeTimers({ shouldAdvanceTime: true })` for both the refresh-on-poll and survive-a-failed-poll behavior.

**The SHA-256-vs-SHA-1 distinction is also an operator-facing gotcha, not just internal — confirmed against a real deployment.** An admin comparing `AgentDetailPage`'s certificate-thumbprint field against a standard local tool on the agent machine (Certificate Manager, PowerShell's `.Thumbprint`, `certutil`, `openssl x509 -fingerprint` without `-sha256`) sees two *different-looking* values for the *same* certificate — those tools default to SHA-1. [Verified live: for real agent `hpn54l`, the server's DB value (`7363BB49AC248E0A3803A7802DE44020F95BADF5F6F62EEC9B4C0B9869BED90E`) was byte-for-byte the correct SHA-256 fingerprint of the local certificate file — the data was never wrong, only unlabeled]. First fixed by labeling the field "(SHA-256)" + a hint with the matching PowerShell/openssl one-liners; later simplified, on user feedback, to just showing both values side by side (`Agent.ClientCertificateThumbprintSha1`, computed alongside the SHA-256 one at issuance time in `InternalCertificateAuthority.IssueAgentLeaf`, display-only — every internal comparison still uses SHA-256 exclusively). If this surfaces again, check the data first before assuming a real mismatch.

**Bug: `Certs:Path` needs an explicit `Certs__Path=certs` env var in the Dockerfile, same as `Database__Path` already has — doesn't default correctly in the container otherwise.** [Found by actually building/running the image]: without it, the container inherits `appsettings.json`'s dev-relative default (`../../certs`), which resolves from `/app` to `/certs` — outside the chowned/volumed directory — and startup fails with `UnauthorizedAccessException`.

**Bug: the csproj's `<Version>` element hit the same class of gap — and broke the Docker publish pipeline outright, not just at runtime.** `UpdateWatch2.Server.csproj`'s `<Version>` (server v0.25.2) reads the repo-root `VERSION` file via `$(MSBuildProjectDirectory)/../../VERSION` — correct from a normal checkout, but the Dockerfile's build stage only ever copies `src/UpdateWatch2.Server/`, never the repo root, so the expression resolved to `/VERSION` with nothing there and `dotnet restore` failed. [Confirmed live: `docker-publish.yml` failed on `main` and both `v0.25.1`/`v0.25.2` tag pushes — neither image was ever published]. Fixed (server v0.25.3) with `COPY VERSION /VERSION` in the Dockerfile's build stage. Re-verify with a real local `docker build -f docker/Dockerfile .`, not just `dotnet build`/`dotnet test`, if you touch `<Version>`/`<Copyright>`/anything else reading a repo-root file by relative path — this is the same "container has a different relative layout than local dev" trap `Certs:Path` demonstrates, and `dotnet test` gave zero warning it was broken.

**Bug: `dotnet ef migrations add` never picks up a non-default C# property initializer as the migration's own `AddColumn` default — always generates the CLR zero-value (`false`, `0`, ...) instead, and that's what an *existing* row gets on an upgrade.** Hit twice building `updatewatch2-server#14` (`AgentAutoUpdateEnabled` should default `true`; `AgentAutoUpdateCheckIntervalHours` should default `6`), both times scaffolding `defaultValue: false`/`defaultValue: 0`. Only matters for an *upgrading* deployment — `AdminSettingsStore.SeedFromDefaults()` already gets a fresh install right, setting every field explicitly from bound `IOptions<T>` defaults. Fix is always the same: open the freshly-scaffolded migration and hand-edit the `AddColumn<T>(...)` call's `defaultValue:` to match the entity's actual intended default before committing — `dotnet ef` never does this for you, no build warning or test failure catches it, only the wrong behavior on a real upgrade. Check for this on every future migration adding a non-nullable column with a non-zero-value intended default.

## Commands (web)

Run from `server/web/`:

```
npm install
cp .env.example .env.local    # point VITE_API_BASE_URL at a running server (default: https://localhost:8796)
npm run dev                   # dev server on :5173
npm run build                 # tsc -b type-check, then production build to dist/
npm test                      # vitest run
```

The toolchain versions in `package.json` (Vite 5, Vitest 2, React 18, TypeScript 5.6) are pinned deliberately, not just whatever `npm create vite@latest` happened to grab — see `web/README.md`'s "Known gaps" for why (a broken peer-dependency graph in the newer Vite/Vitest majors at the time this was scaffolded). Don't casually bump `vite`/`vitest`/`react` to `latest`; if the ecosystem has since stabilized, verify `npm install && npm run build && npm test` still pass clean before committing a bump, and re-check `npm audit`.
